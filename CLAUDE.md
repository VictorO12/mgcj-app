# CLAUDE.md — mgcj-app

This is the React Native / Expo mobile app repo for the M&G C&J taxi dispatch platform. It serves three user roles from one codebase: passenger, driver, and (in some flows) dispatch.

### Role-based entry points

Role branching happens in `App.tsx`'s `RootNavigator`: `useAuth()` exposes `{ session, profile, loading }`. If there's no `session`, the unauthenticated stack renders (`Welcome` → `SignUp`/`PhoneEntry`/`DriverWelcome`/`DriverSignUp` → `OTPVerify`). Once authenticated, `profile?.role === 'driver'` renders `DriverApp`; everything else (passenger, and currently `admin` too — there's no dedicated admin mobile screen) renders `PassengerHomeScreen`. There is no in-app dispatch/admin role screen on mobile; dispatch work happens in the separate `mgcj-dashboard` repo.

### Navigation — `src/navigation/` is empty and unused, not legacy

There is no router living in `src/navigation/`. Navigation happens two ways:
1. **React Navigation native-stack** (`App.tsx`) for the small set of pre-auth screens (`Welcome`, `PhoneEntry`, `SignUp`, `DriverWelcome`, `DriverSignUp`, `OTPVerify`) plus the two post-auth root screens (`PassengerHome`, `DriverHome`). `RootStackParamList` in `src/types/index.ts` defines this.
2. **Manual state-based screen switching** for everything inside the driver and passenger "apps" — this is the dominant pattern, same as `mgcj-dashboard`. `DriverApp.tsx` holds booleans/state (`showAssigned`, `activeRide`, `showAssignedList`, `pendingRide`) and conditionally returns `DriverSetupScreen` / `AssignedRideScreen` / `DriverActiveRideScreen` / `AssignedRidesListScreen` / `DriverHomeScreen`. `PassengerHomeScreen.tsx` does the same with its own boolean flags (`historyVisible`, `profileVisible`, `notificationsVisible`, `helpVisible`, `scheduledVisible`, `paymentVisible`, `driverProfileVisible`) rendering sibling screens as absolutely-positioned full-screen overlays (`<View style={StyleSheet.absoluteFill}>`) rather than via the navigator.

### Key screens

**Auth (`src/screens/auth/`)**
- `WelcomeScreen` — landing screen with passenger signup / login / "I'm a driver" entry points.
- `SignUpScreen` / `PhoneEntryScreen` — passenger name+phone signup and returning-passenger phone login; both send an OTP via `supabase.auth.signInWithOtp` and hand off to `OTPVerifyScreen`. `PhoneEntryScreen` pre-checks registration via the `phone_is_registered()` RPC (security-definer, works pre-session) before sending the code.
- `DriverWelcomeScreen` / `DriverSignUpScreen` — driver-specific onboarding; registration requires a valid, unused `driver_invites` code (validated before the OTP is even sent).
- `OTPVerifyScreen` — verifies the 6-digit SMS code (driver path consumes the invite via the `consume_invite_code` RPC — validate-and-mark-used in one atomic statement; it used to SELECT `driver_invites` directly, which required a policy so open that any anonymous session could enumerate every unused code, and the read-then-mark was a race two devices could both win), then branches: driver path re-validates the invite code, upserts `profiles`+`drivers`, marks the invite used; passenger path checks for a pre-existing **guest profile** (created by dispatch when booking on behalf of an unregistered passenger) keyed by phone number and merges it onto the newly-verified auth user id (including reassigning that passenger's `rides` rows), otherwise upserts a fresh passenger profile.

**Driver (`src/screens/driver/`)**
- `DriverApp` — the driver-side state machine/router described above; owns all ride-fetching, the realtime `rides` subscription, decline/timeout-driven reassignment via `assign-ride`, and notification-tap handling.
- `DriverHomeScreen` — map + online/offline toggle, an "N scheduled rides available to claim" banner (realtime count, opens the Available tab — this is the always-correct channel; the digest push is a rare nudge on top of it) (writes `current_lat/lng` to `drivers` every 10s while online), shows the assigned-ride banner and a horizontally-paged "upcoming scheduled" card panel.
- `DriverActiveRideScreen` — in-ride turn-by-turn screen: polls Google Directions every 30s for ETA/route, advances steps by proximity, detects off-route (>50m from polyline) and auto-reroutes, supports a "nav mode" tilted-camera view, and on completion either calls `capture-payment` (card rides) or opens a cash fare-entry modal.
- `AssignedRideScreen` — full-screen accept/decline view for a single dispatcher-assigned ride (immediate or scheduled); accepting a scheduled ride only sets `confirmed_by_driver`, not `status`.
- `AssignedRidesListScreen` — list of all rides assigned to the driver (immediate + scheduled), with per-card accept/decline and a 10-minute grace window so just-passed scheduled rides don't vanish from sight.
- `RideRequestSheet` — the bottom-sheet ride-offer popup with a 30s countdown timer (auto-declines as a "timeout" rather than a hard decline when it expires); uses a ref for the decline callback to dodge stale-closure bugs.
- `DriverSetupScreen` — one-time vehicle (make/model/year/plate) onboarding gate shown before `DriverHomeScreen` if vehicle fields are unset.
- `DriverEditProfileScreen` — edit name/avatar/vehicle details post-onboarding; avatar upload goes to the `profile-pictures` Supabase Storage bucket.
- `useDriverRating.ts` (in this folder) — **dead code**, see Known Local Issues below.

**Passenger (`src/screens/passenger/`)**
- `PassengerHomeScreen` — the passenger state machine/router: map + address search/autocomplete (Google Places), fare estimation (Directions API distance × flat rate), booking confirmation sheet with a custom inline calendar/time-slot picker for scheduling, card-vs-cash payment selection, and live ride tracking via `useActiveRide`.
- `ScheduledRidesScreen` — list of the passenger's upcoming scheduled rides with cancel action; shows "Finding a driver" for unclaimed `scheduled` rows.
- `PaymentMethodsScreen` — lists saved cards (always shows a non-deletable "Cash" option), set-default/delete actions, links into `AddCardScreen`.
- `AddCardScreen` — Stripe `CardField` collection → `createPaymentMethod` → posts the resulting `pm_...` token to the `save-card` Edge Function.
- `ProfileScreen` — name/avatar/email editing (email is used for receipts) and account deletion (calls `delete-account` Edge Function, then signs out). Note: reads `profile.email`, but `Profile` in `src/types/index.ts` doesn't declare an `email` field — likely a stale type.
- `NotificationsScreen` — notification preference toggles; currently **local-only UI state**, not persisted anywhere (the "Save" button just shows an alert and closes).
- `HelpSupportScreen` (passenger-specific copy) — FAQ accordion + call/email support links.

**Shared (`src/screens/shared/`)**
- `RideHistoryScreen` — used by both roles; lists past rides (role-scoped query), shows/collects driver ratings, and opens `DriverProfileSheet` for passengers. Has a realtime subscription so drivers see new ratings arrive live.
- `HelpSupportScreen` (driver-specific copy, separate from the passenger one of the same name) — driver-oriented FAQ + dispatch contact.

**Components (`src/components/`)**
- `DriverProfileSheet` — bottom sheet showing a driver's avatar/vehicle, aggregate rating breakdown (per-star bar chart), and recent review comments; also surfaces the report-driver entry point and tracks whether the current passenger already reported this ride.
- `ProfileMenu` — the slide-up account menu opened from the avatar button; renders a different item set for driver vs. passenger roles.
- `ReportDriverModal` — passenger-side driver report form (reason codes + optional/required comment); inserts into `driver_reports`, uniqueness enforced by DB constraint (`23505` handled explicitly).
- `RideReviewModal` — passenger-side 1–5 star rating + comment, inserted into `ride_reviews` after ride completion.
- `RideTrackingSheet` — collapsible drag sheet shown to the passenger during an active ride; mini bar vs. expanded view, driver contact actions, cancel logic gated by ride status, and the report-driver entry point.

### Key hooks / context

- `AuthContext` (`useAuth`) — wraps `supabase.auth` session + `profiles` row fetch. Guards against the documented double-fetch-on-mount issue with `fetchingForRef`, and retries the profile fetch (up to 10x, 600ms apart) to ride out trigger/upsert lag right after signup.
- `useActiveRide` — passenger-side hook: fetches/subscribes to the passenger's current active ride (`pending`/`assigned`/`driver_arriving`/`in_progress`), enriches it with driver+profile data, recalculates ETA via Directions API every 30s, and briefly preserves a `completed` ride in state after the row clears so the review modal has time to trigger.
- `useDriverRating` (`src/hooks/`) — the **live** version: fetches a driver's average rating/count from `ride_reviews` and subscribes to realtime `INSERT`s so the average updates without a refetch. The `src/screens/driver/useDriverRating.ts` copy is dead (see below).
- `useNotifications` — registers for Expo push notifications, sets up the driver-only `RIDE_REQUEST` notification category (Accept/Decline action buttons), and writes the resulting token to `drivers.push_token` (drivers) and `profiles.push_token` (everyone).

## OTA updates (expo-updates) — added 2026-08-23

`expo-updates` is installed and wired: `updates.url` + `runtimeVersion: { policy: "fingerprint" }` in `app.config.js`, and a `channel` on all three `eas.json` build profiles (**a build with no channel receives nothing** — none had one before). Config rationale and footguns: `.claude/notes/ota-updates-expo-updates.md`; the runtime design (when it checks, when it applies, what it shows) and its test plan: `.claude/notes/ota-runtime-design.md`. Six things to keep in mind:

- **`fallbackToCacheTimeout: 4000`, deliberately not `0`.** `0` launches from cache and downloads in the background, which is the setting *least* able to handle a launch crash — the exact incident this exists for: the crash races the download and usually wins, so the fix never lands. `4000` blocks at the native splash and launches the *replacement* bundle, so the fix applies on the first relaunch. Don't "optimise" it back to 0.
- **Never switch `runtimeVersion` to the `appVersion` policy** — bumping `version` would orphan every installed build from future updates. `fingerprint` also changes when native deps change, which is what stops a JS bundle landing on a binary missing a native module it calls. `eas.json`, `.gitignore` and dependency versions are all fingerprint *sources* — settle them (incl. `npx expo install --fix`) **before** cutting a build, or the first housekeeping commit orphans it.
- **It does nothing until a build carrying it is on devices** (native module). Bundle with the unshipped `last_seen_at` heartbeat build.
- **`extra` is resolved at publish time, not just build time.** `app.config.js` reads `process.env.SUPABASE_URL`/`SUPABASE_ANON_KEY`/`STRIPE_PUBLISHABLE_KEY`/`GOOGLE_MAPS_ROUTING_KEY`; an `eas update` run without those resolvable ships a bundle with undefined credentials — an app that launches then fails every query. Pass `--environment` explicitly. **Blocker:** `eas env:list preview` and `production` are both currently *empty* (only `development` has vars), so a preview/production build ships broken today, independent of OTA.
- **The reload gate is NOT `interstitialGateOpen`.** That predicate means "is it rude to show a card"; a reload means "is it safe to destroy all in-memory state", and they differ both ways. `useOtaUpdate` takes a `ReloadBlock` (`none`/`soft`/`hard`): HARD = active ride or unsaved booking input, SOFT = overlays. It applies **only on foreground resume** (mid-session a reload is indistinguishable from a crash), and a blocker this device has watched for >2h is treated as stuck state and overridden — otherwise an E7-style stuck ride permanently starves the device of the fix for it. That clock is keyed to the **blocker's id** and persisted (`ota.blockSince`): timing the block *state* resets on every remount, and timing the *pending update* would reload a ride that started seconds ago. The driver hook mounts in **`DriverApp`**, not `DriverHomeScreen`, for exactly that reason.
- **`extra` is hashed into the fingerprint** (measured). So per-publish metadata must never ride in `extra` — it would change the runtime version and orphan every build — and the env used at `eas update` must byte-match the env used at `eas build` or updates silently never land. Also: rotating any key in `extra` is a store-build event.
- **OTA cannot rebrand a demo build.** It ships JS + assets only — in-app copy yes, app icon / app name / splash / bundle ID no. Per-company pitch branding needs a runtime read of the company row; the app currently has **zero** `from('companies')` calls and hardcodes branding in 8+ files.

- Dark theme color palette is hardcoded per-screen (`#111827` background, `#E8500A` passenger/brand orange, `#1D9E75` driver/online green, `#A855F7` purple for anything scheduled-ride-related) — no centralized theme file yet.

- **Driver nav route geometry comes from the per-step polylines, not `overview_polyline`** (`DriverActiveRideScreen.tsx` `fetchRoute`, 2026-07-27): the Directions `overview_polyline` is decimated, and driving *and* the off-route test both read off it caused false "Rerouting…" on long straights (an on-road driver sat >80 m from the nearest coarse vertex) and corner-cutting on curves. Fix concatenates `steps[].polyline.points` (full-res, same response, $0) with the shared seam-vertex deduped; overview is only a fallback. Off-route thresholds were then tightened to 50 m / 3 s (were 80 m / 5 s, slack for the coarse line). Don't revert to `overview_polyline` for either purpose.

## Internal auth for cron-called functions — read before touching keys

`requireServiceRole` (`functions/_shared/internalAuth.ts`) gates the functions only pg_cron or another Edge Function may call. It accepts **either**:

- `x-internal-key: <INTERNAL_API_KEY>` — a secret we own, and the only path that works for pg_cron, or
- `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>` — kept because function-to-function calls send their own env var and match by construction.

**Why two paths** (incident 2026-08-15, cost hours): the gate originally compared only against the injected `SUPABASE_SERVICE_ROLE_KEY`. This project has the **new Supabase API key system** enabled, and the value injected into the Edge Function runtime is **not** the legacy `service_role` JWT that the cron jobs carry — so every gated cron 401'd the moment the gate deployed. `expire-pending-rides`, `scheduled-coverage-monitor`, `sweep-held-transfers` and `scheduled-ride-digest` all silently stopped: auto-cancel, coverage + the stale-driver reaper, held-transfer sweeps, and driver notifications.

Three traps worth keeping:

1. **The crons were never wrong.** Their bearer token is byte-identical to the working key vellon-ops uses against this project. Re-stamping them was the obvious fix and it was useless — the runtime's key was the odd one out. Verify by fingerprint (`md5()`), never by assumption.
2. **The failure is invisible where you'd look.** `cron.job_run_details` reports **success**, because `net.http_post` only enqueues. The HTTP status lands in `net._http_response` — that is the only place a 401 here shows up.
3. **A custom header is required, not just a different bearer.** `scheduled-ride-digest` and `sweep-held-transfers` have no `config.toml` block, so `verify_jwt` defaults to **true** and the gateway rejects any non-JWT bearer before our code runs. Cron sends both headers: the JWT satisfies the gateway, `x-internal-key` satisfies the gate.

**Before disabling the legacy `service_role` key** (planned during the parked key rotation): these four cron jobs still send it on `Authorization` to satisfy the gateway. Disabling it re-breaks all four — and they are load-bearing for missed-ride cancellation and payment sweeps. Re-stamp first, then disable. See `20260749_cron_internal_api_key.sql`, which rewrites a job's headers while carrying its existing bearer token across untouched.

**Rule: never gate on a platform-injected key you cannot inspect.**

## Supabase Edge Functions (`supabase/functions/`)

- **`assign-ride`** — Core auto-dispatch: on a new `pending` ride (or an explicit decline/timeout callback), filters to online+free drivers, Haversine-prefilters to the closest 5, picks the true-fastest by Google Distance Matrix, and assigns with an optimistic-lock update (`.eq('status','pending')`) to avoid double-assignment races. Implements the two-pass decline/timeout cycling described in the root CLAUDE.md. If no drivers are available at any point it just gives up silently (`reason: 'no_drivers'`/`'all_declined'`) — the admin push here (`notifyDispatchNoDrivers`) was removed 2026-07-12 (dispatch never uses the mobile app); dispatch has no dedicated indicator for this state yet, they'd need to notice the ride still sitting `pending`/`offered` and use the dashboard's existing "Assign driver" override.
- **`broadcast-scheduled-ride`** — Repurposed (2026-07-06) from a driver-facing "ride available" broadcast into a booking-time coverage check. Fires on INSERT of a new `scheduled` ride: computes `coverage_status` (`uncovered`/`at_risk`/`covered`) from the company's driver roster and stamps it on the ride; if `preferred_driver_id` is set, sends that driver a non-binding heads-up push. No longer solicits drivers to claim — that path was removed; advance driver-facing claiming now happens only via the pull-based "Available" list (`fetchOpenRides` in `AssignedRidesListScreen`). The admin push on `uncovered` was removed 2026-07-12 — dispatch reads `coverage_status` off the dashboard instead (though note: the dashboard's `coverageDisplay()` currently hardcodes "Healthy" for any ride scheduled >24h out regardless of the real `coverage_status`, so a structural `uncovered` gap booked weeks ahead won't show truthfully yet — flagged, not yet fixed).
- **`claim-scheduled-ride`** *(added 2026-08-15)* — Driver-triggered soft claim / un-claim of a scheduled ride from the "Available" board. Writes `preferred_driver_id` (never exclusive) + `claimed_at`, leaving `driver_id` NULL and `confirmed_by_driver` untouched, so the ride stays in `scheduled-release`'s normal pipeline. Needs the service role because RLS's `WITH CHECK (driver_id = auth.uid())` means the only claim a client can write is one that hard-binds the driver. Race-safe via `.is('preferred_driver_id', null)`, which also stops a driver overwriting a dispatch-set preference. Does **not** touch `coverage_status` — a non-binding claim adds no reachable capacity, and the coverage sites only count a preference when it's exclusive.
- **`dispatch-assign-ride`** *(added 2026-08-15)* — Dispatch's manual assign/reassign, moved out of `mgcj-dashboard`'s `assignDriver()` (which used to write `rides.driver_id` directly). It must clear `preferred_driver_id`/`claimed_at` in the same write as `driver_id`: a leftover claim made `scheduled-release` hand the ride back to the old claimant on its next tick, silently undoing dispatch. Also pushes the displaced claimant. `logDispatchEvent` stays client-side so the dispatcher remains the recorded actor.
- **`capture-payment`** — Driver-triggered (on ride completion) Stripe PaymentIntent capture for card rides; recalculates the platform fee/transfer split from the company's `platform_fee_percent` and only sets `transfer_data[amount]` if the company has a `stripe_account_id` (Connect-onboarded).
- **`create-payment-intent`** — Passenger-triggered, called at booking time for card rides; creates a manual-capture (hold-only) Stripe PaymentIntent against the passenger's saved default card, with friendly decline-reason mapping.
- **`decline-assigned-ride`** *(added 2026-07-12)* — Driver-triggered decline of an unconfirmed dispatch-assigned scheduled ride (`AssignedRideScreen`/`AssignedRidesListScreen`, `status === 'scheduled'` path only — immediate `'offered'` declines still go through `assign-ride` with `declined_by_driver_id`, unchanged). Exists because RLS's `"Drivers can update their rides"` policy has `WITH CHECK (driver_id = auth.uid())`, so a driver can never null their own `driver_id` from the client — a direct `.update({ driver_id: null })` is silently rejected by Postgres. Runs with the service role: clears `driver_id`/`confirmed_by_driver`, recomputes `coverage_status` properly (same roster/active-driver logic as `broadcast-scheduled-ride`, scoped to `vehicle_class_id` if set — does **not** hardcode `'uncovered'`), and appends to `declined_by` via `append_declined_by` (deduped as of migration `20260712_dedupe_declined_by.sql` — it was a bare `array_append` before). No push is sent — dispatch works from the dashboard, not push; visibility is via the `coverage_status` Realtime toast/pill plus a "Declined by" row in the ride-detail modal (`mgcj-dashboard`). Since `status` stays `'scheduled'` with `driver_id` cleared, the ride automatically re-enters `scheduled-release`'s normal dynamic pipeline on the next tick.
- **`scheduled-ride-digest`** *(added 2026-08-15; cron `*/15 * * * *` **registered and verified live 2026-08-16** — an end-to-end push was confirmed on a real device)* — Tells a driver, **once per ride, per time that ride becomes available**, that new claimable scheduled work has appeared on the Available board. Content-triggered, not time-triggered: there is deliberately **no clock constant in the design** because these companies run 24h, so any hour is wrong for whoever is asleep or driving (the first cut fired daily at 6pm about "tomorrow" — both halves were wrong for a 24h fleet, and "tomorrow" is meaningless at 2am to a driver whose shift starts at 8pm). Quiet hours are intentionally **not** implemented — iOS Focus / Android DND already solve it per-person and handle a night driver's hours being the inverse of a day driver's. State: `drivers.digest_watermark_at` (highest `rides.became_open_at` announced to them) + `drivers.digest_last_sent_at`, both from `20260747`. **Two-tier rate ceiling** (6h normally, 1h when a new ride's pickup is inside 12h): a single 6h floor let a ride booked at noon for 6pm release to the pool before anyone heard of it; the 12h is a cheap proxy for "the claim window is closing", not a meaningful number. Counterintuitive but load-bearing: **a bigger fleet wants a LONGER interval, not shorter** — at thousands of rides/day the board is never empty, so "new work exists" carries no information. Three correctness details: a NULL watermark **seeds silently** (a new/reinstalled driver must not get the whole backlog as their first push), the message states the **new** count and never the running total (restating known work reintroduces the fatigue through the body), and the watermark advances **only for Expo tickets that came back `ok`** (advancing on a dead token would silence those rides for that driver forever). Audience is every driver with a `push_token` — the **one driver-read site that must not use `isDriverDispatchable()`**. All timing logic lives in `shouldSendDigest()` so future work (driver-set frequency, holding until not mid-ride, learned windows — the last blocked on the `last_seen_at` heartbeat build) is one predicate, not a rewrite.
- **`delete-account`** — Passenger-only self-service account deletion: nulls `passenger_id` on their `rides`/`ride_reviews` (keeps records, detaches them), deletes the `profiles` row, then deletes the Supabase Auth user.
- **`edit-ride`** *(added 2026-08-16)* — Passenger (or dispatch) edits to a ride that is still happening: `reschedule` (move `scheduled_at`) and `relocate` (move pickup and/or dropoff, re-pricing the ride). Exists because the fare and the thing the fare is computed FROM have to move together: `guard_ride_fare_fields` already froze `fare_estimate`, and `20260751` extends that freeze to the pickup/dropoff coordinates and `scheduled_at`, so a client `.update()` can no longer rewrite the destination while the fare stays pinned at the old cheap number. It absorbed the old client-side time edit in `ScheduledRidesScreen` for the same reason `settle-ride` absorbed four callers doing bare status writes — one place decides what a change resets. Three things are load-bearing: **(a) mid-ride pricing is `driven + remaining`, never `pickup → new dropoff`** — the naive version is a free-ride exploit (ride twenty minutes out, redirect to somewhere near the pickup, pay a minimum fare) — computed as one Directions call with the driver's live `current_lat/lng` as a waypoint, read per-leg so the commitment check reuses it. **(b) The Stripe ordering is the INVERSE of `settle-ride`'s**: the new hold is taken first, the row written only if it succeeds, the old hold cancelled last, because here the hazard is a live ride with no money behind it rather than a dead ride still holding some. A declined card refuses the edit and the ride continues to its original destination. The hold is re-taken whenever the amount moves **either way** — a *decrease* is the dangerous direction, since `capture-payment` captures `amount_capturable ?? amount` off the PI and writes it back over the fare, so a shortened trip left on the old authorization overcharges with a receipt that agrees. **(c) A moved time or pickup releases a soft claim and pushes the claimant** (a moved destination does not — they're still being asked for the job they claimed); a claimed ride has `driver_id` NULL, so the old `.is('driver_id', null)` guard let a passenger move a ride out from under a claimant silently. Also runs the `_shared/commitment.ts` guard — a destination change is the "will this make the driver late for a booked pickup" hazard arriving through a different door, and was the one case `assign-ride`'s guard didn't cover. **Dispatch folded in 2026-08-16** (was listed here as an open gap): `mgcj-dashboard`'s `saveRideEdits` now calls this function instead of writing `rides` directly. The gap was mis-stated while open — it *did* re-price client-side, so the fare was never stale; what it could not do is move the **Stripe authorization**, and `capture-payment` captures the PI's amount and writes it back over the fare, so a dispatcher's destination change produced a charge and a receipt that agreed with each other and disagreed with the ride. `relocate` takes admin-only extras on the same call (`scheduled_at`, `vehicle_class_id`, `fare_override`, `confirm_conflict`) because a dispatcher's save is one atomic edit; `reschedule` is untouched. Admin differences are deliberate: no `MAX_EDITS` cap (its message tells passengers to call dispatch, so applying it to dispatch closes the door it points at), pickup movable until the passenger is aboard rather than until a driver is assigned, and a commitment clash is a confirmable warning rather than a refusal. A moved pickup **or** time now clears `confirmed_by_driver` and re-asks the driver, and pushes the passenger. **`fare_override` is pre-discount** — `fare_estimate` is post-discount everywhere else, so seeding the dashboard's fare box from it would subtract the discount twice on every save. A time-only edit skips the pricing block entirely: no Directions call, no Stripe round trip.
- **`expire-pending-rides`** — Cron: cancels `pending` immediate rides older than 5 minutes (notifies the passenger), and for rides pending 2–5 minutes, clears `declined_by` and re-triggers `assign-ride` to give all drivers another shot.
- **`notify-dispatch-report`** *(added 2026-07-12)* — Fired by a Supabase Database Webhook (configured in the dashboard, not SQL — webhook name `notify-dispatch-report`) on INSERT of a new `dispatch_reports` row (see `mgcj-dashboard`'s Settings → Support tab). Looks up the company and submitting admin's names and emails `support@vellon.ca` via Resend with the category, company, submitter, and message. Company-wide report visibility (any admin at a company sees all reports filed there) is enforced by RLS on `dispatch_reports`, not by this function.
- **`notify-drivers`** — **Deprecated**, replaced by `assign-ride`; current implementation is just a no-op stub.
- **`notify-passenger`** — Fires on ride UPDATE; pushes the appropriate passenger notification per status transition (assigned-and-confirmed, arriving, in-progress, completed-with-fare, cancelled). Explicitly skips notifying on `assigned` until `confirmed_by_driver` flips true, so passengers aren't told "driver on the way" before the driver has actually accepted.
- **`notify-review`** — Fires on `ride_reviews` INSERT; pushes a star-rating notification (with running average) to the rated driver.
- **`reassign-stale-rides`** — Cron: finds any ride `status='offered'` with `offered_at` >60s ago (covers immediate rides *and* released scheduled rides, not immediate-only). Branches on preferred-driver exclusivity: non-exclusive/soft-preferred rides call `assign-ride` with `timed_out_driver_id` (eligible again on a second cycling pass, same as before); an **exclusive** preferred-driver ride never falls through to a stranger — instead it re-pings the preferred driver, resets `offered_at` so the 60s window restarts, and flips `coverage_status` to `at_risk`. The admin push on that degradation was removed 2026-07-12 — dispatch reads `coverage_status` off the dashboard instead. Note (2026-07-12): exclusive immediate rides are moot in practice — dispatch is the only place `preferred_driver_exclusive` can be set, and it's only exposed on scheduled bookings, so this exclusive-path branch effectively only ever fires for scheduled rides.
- **`save-card`** — Passenger-triggered; gets-or-creates a Stripe Customer for the passenger, attaches the submitted PaymentMethod, fetches its display details, and stores it in `payment_methods` (first card saved becomes the default automatically).
- **`scheduled-release`** *(current, cron `*/2 * * * *`)* — Per-ride dynamic release: fetches `scheduled` rides with `scheduled_at` within 75 min, computes a release threshold from drive-time to the 3rd-nearest available driver (or the preferred driver, if set) plus an 8-min churn buffer, clamped 10–75 min. Once inside that threshold, flips the ride to `pending` + invokes `assign-ride` (pool) or `offered` with `driver_id` set directly (preferred driver, stamping `leave_by`/`pickup_eta_mins`). If zero drivers are available it holds and rechecks every tick, force-releasing anyway once inside the 10-min floor so dispatch can intervene manually via the dashboard's assign-driver override. Also sends passenger T-30/T-15 push+SMS reminders (`notified_30min`/`notified_15min`), driver departure-time pushes once `leave_by` arrives (`departure_notified`), and lazily creates the deferred Stripe PaymentIntent for card rides just before release. `markAtRiskAndAlert` (exclusive preferred driver unavailable right at release) writes `coverage_status='at_risk'` only — the admin push it used to send was removed 2026-07-12.
- **`scheduled-coverage-monitor`** *(current, cron `*/10 * * * *`)* — Read-only-in-intent: recomputes `coverage_status` for every open scheduled ride and writes it if changed. Sends no push itself — degradation surfaces via Realtime on the dashboard (rollup coverage bar + toast) rather than a notification.
- **`send-ride-receipt`** — Fires on ride UPDATE transitioning to `completed`; emails an HTML receipt via Resend to the passenger's profile email, if one is set (currently sends from Resend's shared test domain — only deliverable to the developer's own verified address until a custom domain is verified).
- **`send-sms`** — Internal-only helper wrapping Twilio's SMS API; called by `scheduled-release` for driver/passenger pickup reminders. **Gated by `requireServiceRole` since 2026-08-15** — it previously carried a comment claiming Supabase validated the service-role key automatically when `verify_jwt = false`, which is false: that setting disables the gateway check outright, and a POST with no `Authorization` header at all reached the function body (verified live). Anyone knowing the URL could send arbitrary SMS on the project's Twilio account. Also **no longer no-ops quietly** when Twilio secrets are missing: it returned `200 {skipped:true}`, which passed `scheduled-release`'s `if (!res.ok)` check and logged nothing, so every T-30/T-15 passenger reminder had been silently dropped since launch with no trace. Now returns `503` naming the missing secrets.
- **`stripe-webhook`** — Verifies Stripe's HMAC signature (rejecting payloads >5 min old) and syncs `rides.payment_status` on `payment_intent.succeeded` / `.payment_failed` / `.canceled` and `charge.refunded` events.

**Legacy/dead (superseded, unscheduled — safe to delete):** `scheduled-lifecycle` (old unified cron: fixed T-30/T-15 reminders, travel-time auto-start, 60-min unclaimed escalation via an `escalated` flag), `process-scheduled-rides`, `scheduled-ride-reminders` (read a nonexistent `profiles.expo_push_token` column), `schedule-rides`.
